In Kubernetes, cgroups are the low-level Linux kernel mechanism that turns your Pod's `resources.requests` and `resources.limits` from configuration into actual, enforced system behavior. They are the invisible engine that guarantees resource isolation and fairness across all workloads on a node.

### The Flow: From Pod Spec to Kernel Enforcement

The journey from a Pod manifest to enforced limits is a collaboration between the API server, scheduler, kubelet, and container runtime.

1.  **You Define Resources**: In your Pod's YAML, you specify `requests` (minimum guaranteed resources) and `limits` (maximum allowed resources).
2.  **Scheduler Uses Requests**: The kube-scheduler uses the `requests` to decide which node has enough available resources to place the Pod.
3.  **Kubelet Takes Over**: Once scheduled, the kubelet on that node reads the Pod's configuration.
4.  **Runtime Creates cgroups**: The kubelet passes the resource configuration to the container runtime (e.g., containerd, CRI-O).
5.  **Kernel Enforces Limits**: The runtime creates the necessary cgroups and writes the `requests` and `limits` values to the appropriate cgroup files. The Linux kernel then uses these cgroups to enforce the rules.

For example, a container with `cpu: "250m"` and `memory: "128Mi"` will have its cgroup configured to guarantee 250 millicores of CPU and reserve 128 MiB of memory, and to throttle CPU at its limit or OOM-kill the pod if it exceeds its memory limit.

### The Three-Tier cgroup Hierarchy

To manage resources effectively, Kubernetes organizes cgroups in a specific hierarchy. This structure is primarily managed by the kubelet's Container Manager.

1.  **Node Root (`/kubepods`)**: The top-level cgroup for all Kubernetes workloads. The kubelet itself can also be placed in a separate cgroup (`/kube-reserved`) to protect system services.
2.  **QoS Level**: Below the root, Pods are grouped by their **Quality of Service (QoS) class**. This is Kubernetes' primary mechanism for prioritizing workloads under resource pressure.
    *   **Guaranteed**: Pods where `requests` equal `limits` for all resources. They get the strongest cgroup guarantees and are evicted last.
    *   **Burstable**: Pods where `requests` are less than `limits` for at least one resource. They have limited enforcement but are prioritized over BestEffort pods.
    *   **BestEffort**: Pods with no `requests` or `limits` defined. They get no guarantees and are the first to be evicted.
3.  **Pod and Container Level**: Within each QoS class, there's a cgroup for each individual Pod, and within that, a cgroup for each container in the Pod. This allows for granular resource control.

This hierarchy enables the kubelet to make informed eviction decisions. For instance, under memory pressure, it will kill BestEffort pods first, then Burstable, and finally Guaranteed pods, ensuring the most critical workloads survive.

### The cgroup Driver: systemd vs. cgroupfs

The kubelet and the container runtime use a **cgroup driver** to manage the cgroup hierarchy. The two main options are:

*   **`systemd` (Recommended)**: The cgroups are managed by systemd. This is the default and strongly recommended driver on modern Linux distributions, especially with cgroup v2. It ensures better integration and avoids conflicts with system-level processes.
*   **`cgroupfs`**: The kubelet and runtime directly manipulate the cgroup filesystem (`/sys/fs/cgroup`). This is considered a legacy approach and is not recommended for production.

**It is critical that the kubelet and the container runtime use the same cgroup driver** to prevent issues. In Kubernetes v1.28 and later, the `KubeletCgroupDriverFromCRI` feature gate allows the kubelet to automatically detect the driver from the runtime, simplifying configuration.

### cgroup v2: The Current Standard

Kubernetes has supported cgroup v2 as a stable feature since version 1.25. It is the recommended version and is becoming the default on all modern Linux distributions.

Key advantages of cgroup v2 in Kubernetes include:
*   **A single, unified hierarchy** which is simpler to manage and introspect.
*   **Safer sub-tree delegation** to containers.
*   **Enhanced resource management**, such as the MemoryQoS feature for improving memory quality of service.

The kubelet and container runtime automatically detect and adapt to cgroup v2, typically requiring no additional configuration.

### Summary

In essence, Kubernetes uses cgroups to provide a robust, multi-layered resource management system that is both declarative (via the Pod spec) and imperative (via the kernel). By combining `requests` and `limits` with a QoS-based cgroup hierarchy, Kubernetes ensures that workloads are isolated, resources are fairly distributed, and the node remains stable under pressure.
