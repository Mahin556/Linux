# 🎯 Why Use a Group-Based Approach (cgroups)?

The group-based approach (cgroups) is used because it allows you to **manage, limit, and monitor resources for multiple processes as a single unit**, rather than individually. This is essential for system stability, fairness, and predictability in multi-tenant environments.

## 🎯 Key Reasons to Use Group-Based Approach

### 1. Resource Isolation and Guarantees

| Without Groups | With Groups |
|----------------|-------------|
| Process A can consume 100% CPU | Process A limited to 50% CPU |
| Process B crashes due to memory leak | Memory leak contained within group |
| System becomes unstable | System remains stable |
| All processes affected | Only affected group impacted |

## 📊 Real-World Use Cases

### 1. Docker Containers

```bash
# Docker uses cgroups behind the scenes
docker run --cpus=0.5 --memory=256m nginx
```
**What happens:** Docker creates a cgroup for the container with CPU and memory limits.

### 2. Kubernetes Pods

```yaml
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: app
    resources:
      limits:
        cpu: "500m"
        memory: "256Mi"
      requests:
        cpu: "250m"
        memory: "128Mi"
```
**What happens:** Kubernetes uses cgroups to enforce these limits.

### 3. System Services

```bash
# systemd uses cgroups for service management
systemd-run -p CPUQuota=50% -p MemoryMax=500M my_service
```
**What happens:** Systemd creates a cgroup for the service with resource limits.

### 4. Batch Processing

```bash
# Limit batch jobs to prevent system slowdown
# All jobs in the batch group share the same limit
cgcreate -g cpu,memory:/batch
cgset -r cpu.max="50000 100000" batch
cgset -r memory.max="2G" batch

# Run all batch jobs in this group
cgexec -g cpu,memory:batch ./job1.sh &
cgexec -g cpu,memory:batch ./job2.sh &
cgexec -g cpu,memory:batch ./job3.sh &
```

## 🆚 Comparison: Individual vs Group-Based

| Aspect | Individual Management | Group-Based (cgroups) |
|--------|----------------------|----------------------|
| **Management** | Each process individually | All processes as a unit |
| **Scalability** | Hard to manage many processes | Easy to manage groups |
| **Resource Guarantees** | No guarantees | Hard guarantees |
| **Fairness** | No fairness | Fair distribution |
| **Isolation** | No isolation | Strong isolation |
| **Multi-tenancy** | Not feasible | Feasible |
| **Performance** | Unpredictable | Predictable |
| **System Stability** | Unstable | Stable |
