# 🔄 Is Direct cgroupfs Change Persisted?

**NO — Direct changes to cgroupfs are NOT persisted.**

When you write directly to `/sys/fs/cgroup/...`, you are modifying the **kernel's in-memory state**, not a configuration file on disk. These changes are **ephemeral** and will be **lost on reboot**.

---

## 📊 What Happens to Direct cgroupfs Changes?

| Scenario | Result |
|----------|--------|
| **After reboot** | ❌ All limits are reset to default |
| **After service restart** | ❌ Systemd may reset the cgroup |
| **Systemd reload** | ❌ Systemd may override your changes |
| **Container restart** | ❌ Container runtime resets cgroups |

---

## 🔍 Why Are They Not Persisted?

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    cgroupfs is a Pseudo-Filesystem                         │
│                                                                             │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │                    /sys/fs/cgroup/                                   │   │
│   │                                                                     │   │
│   │   • Files are created in memory (RAM)                              │   │
│   │   • Not stored on disk (hard drive)                                │   │
│   │   • Changes affect kernel state                                    │   │
│   │   • Reset when the kernel restarts (reboot)                       │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│   ❌ Writing to /sys/fs/cgroup/ is like changing a running process's     │
│      memory — it's temporary and lasts only as long as the system runs   │
└─────────────────────────────────────────────────────────────────────────────┘
```

## ⚙️ What Happens After Reboot?

### Example: Before Reboot

```bash
# Set CPU limit directly
echo "50000 100000" | sudo tee /sys/fs/cgroup/system.slice/my.service/cpu.max
echo "500M" | sudo tee /sys/fs/cgroup/system.slice/my.service/memory.max

# Verify it works
cat /sys/fs/cgroup/system.slice/my.service/cpu.max
# Output: 50000 100000
```

### After Reboot

```bash
# Check the same file
cat /sys/fs/cgroup/system.slice/my.service/cpu.max
# Output: max 100000  (default — NO limit!)
```

**The limit is gone!** 🗑️

## ✅ How to Make Changes Persistent

Since direct cgroupfs changes are not persisted, you need to use methods that **create configuration files on disk**.

### Method 1: systemd Service Override (Recommended)

```bash
# Create a persistent override file
sudo mkdir -p /etc/systemd/system/my.service.d/
sudo tee /etc/systemd/system/my.service.d/override.conf <<'EOF'
[Service]
CPUQuota=50%
MemoryMax=500M
EOF

# Reload and restart
sudo systemctl daemon-reload
sudo systemctl restart my.service
```

**Why this works:** The override file is stored on disk (`/etc/systemd/system/`), so it survives reboots.

### Method 2: systemctl set-property with --runtime=false

```bash
# Set properties persistently (survives reboot)
sudo systemctl set-property my.service CPUQuota=50% --runtime=false
sudo systemctl set-property my.service MemoryMax=500M --runtime=false
```

**Why this works:** systemd writes the limits to a persistent drop-in file automatically.

### Method 3: Modify the Service Unit File Directly

```bash
# Edit the service file
sudo systemctl edit --full my.service

# Add these lines to the [Service] section:
# CPUQuota=50%
# MemoryMax=500M

# Save and reload
sudo systemctl daemon-reload
sudo systemctl restart my.service
```

## 📋 Comparison Table

| Method | Persisted? | Survives Reboot? | Survives Service Restart? |
|--------|------------|------------------|---------------------------|
| **Direct cgroupfs write** | ❌ No | ❌ No | ❌ No |
| **systemctl set-property (runtime)** | ❌ No | ❌ No | ❌ No |
| **systemctl set-property (--runtime=false)** | ✅ Yes | ✅ Yes | ✅ Yes |
| **Service override file** | ✅ Yes | ✅ Yes | ✅ Yes |
| **Edit service file** | ✅ Yes | ✅ Yes | ✅ Yes |

## 💡 When to Use Direct cgroupfs

### ✅ Good Use Cases

| Scenario | Why |
|----------|-----|
| **Quick testing** | Instant changes without restarting services |
| **Debugging** | See immediate effects |
| **One-off temporary changes** | Changes that don't need to persist |
| **Emergency throttling** | Stop a runaway process immediately |

### ❌ Bad Use Cases

| Scenario | Why |
|----------|-----|
| **Production permanent limits** | Won't survive reboot |
| **Long-term configuration** | Needs to be stored on disk |
| **Controlled environments** | Not auditable or manageable |
| **Team environments** | No visibility for other admins |

## 🔍 How to Check What's Persisted

```bash
# Check the service's drop-in files
ls -la /etc/systemd/system/my.service.d/

# View the content
cat /etc/systemd/system/my.service.d/50-CPUQuota.conf

# Check current properties
systemctl show my.service | grep -E "CPUQuota|MemoryMax"

# Check current cgroup values
cat /sys/fs/cgroup/system.slice/my.service/cpu.max
cat /sys/fs/cgroup/system.slice/my.service/memory.max
```
