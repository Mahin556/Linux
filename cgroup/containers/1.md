Both Docker and Podman rely on the Linux kernel's **cgroups** feature to enforce resource limits and provide isolation. The fundamental mechanism is the same, but there are significant differences in their architecture, especially regarding daemons and rootless operation.

---

### 🐳 How cgroups Work in Docker

Docker uses a **client-server architecture** with a central daemon (`dockerd`) that manages containers and their cgroups.

1.  **Daemon-Driven**: When you run `docker run --memory=512m`, the CLI sends a request to the `dockerd` daemon.
2.  **Daemon Creates cgroup**: The daemon then uses the kernel's cgroupfs interface to create a new cgroup under a parent like `/sys/fs/cgroup/system.slice/docker-<container_id>.scope/`.
3.  **Applies Limits**: The daemon writes your requested limits (e.g., `512M` to `memory.max`) to the files within that container's cgroup directory.
4.  **Moves Process**: Finally, it places the container's main process PID into that cgroup's `cgroup.procs` file, activating the limits.

The Docker daemon itself is typically managed by systemd, and in many configurations, it will place containers within the `docker.slice`.

### 🐧 How cgroups Work in Podman

Podman is **daemonless**. It uses a **fork/exec model** where the `podman` CLI command directly interacts with the kernel.

1.  **Direct Interaction**: When you run `podman run --memory=512m`, the `podman` process communicates directly with the kernel (via `runc` or `crun`) to create the container.
2.  **Creates cgroup**: The runtime creates a new cgroup for the container, often as a sub-cgroup of the systemd user or system slice.
3.  **Applies Limits**: The resource limits you specify are written to the container's cgroup directory.
4.  **Moves Process**: The container's main process is moved into the new cgroup.

Because there's no daemon, Podman's model is generally considered more lightweight and secure.

---

### 🆚 The `systemd` Cgroup Manager

A key difference lies in how they integrate with `systemd`.

- **Docker**: Traditionally used its own `cgroupfs` manager, but in modern setups with cgroups v2, it can and often does use `systemd` as the cgroup manager. In fact, on some systems, resource limiting is only fully supported when using cgroups v2 **and** the `systemd` cgroup manager.
- **Podman**: Natively and strongly integrates with `systemd`. By default, Podman uses `systemd` as its cgroup manager, creating containers as transient systemd units (scopes or services). This provides better integration with the host's resource management system.

### ⚖️ Rootless Operation: A Major Divergence

This is where the two tools differ most significantly.

- **Docker**: Running containers in **rootless mode** has historically been complex and is not the default behavior. It can be challenging to set up and has limitations.
- **Podman**: **Rootless operation is a primary design goal** and works seamlessly out of the box. A non-root user can run containers.
    - **Requirement**: Rootless Podman **requires cgroups v2** (the unified cgroup hierarchy). It also relies on user namespaces for user mapping.
    - **Limitation**: While rootless Podman can limit resources, it may have limitations on which cgroup controllers it can use. For example, some rootless Podman users have reported issues with the `pids` controller, and the kernel does not support cgroup delegation with cgroups v1.
    - **Cgroup Management**: Rootless Podman uses the `systemd` cgroup manager for resource control.

### 📊 Comparison Table

| Feature | Docker | Podman |
| :--- | :--- | :--- |
| **Architecture** | Client-Server (Daemon) | Daemonless (Fork/Exec) |
| **Cgroup Management** | `cgroupfs` or `systemd` | Defaults to `systemd` |
| **Rootless Mode** | Supported but not default | **Primary design goal** |
| **Cgroups v2** | Supported | **Required** for rootless operation |
| **systemd Integration** | Supported | **Deeply integrated** (default manager) |

### 💎 Summary

In essence, both Docker and Podman use the same underlying Linux kernel mechanism (cgroups) to limit container resources. The key differences lie in their operational models:

- **Docker** is a daemon-based system that uses cgroups to enforce the limits you request.
- **Podman** is a daemonless system that interacts with cgroups more directly, prioritizing rootless operation and deep integration with `systemd`.

This fundamental architectural choice significantly impacts how they manage resources, particularly in rootless environments where Podman's design offers a clear advantage.
