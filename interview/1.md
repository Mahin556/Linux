## 🕒 How to Troubleshoot a Cron Job That Isn't Running

If your cron job fails to execute, follow this systematic checklist to identify and fix the issue.

---

### 1️⃣ **Check System Time & Timezone**
Cron relies on the system's local time. If the time is wrong, the job may run at an unexpected hour—or not at all.

```bash
# Show current date and time
date

# Show timezone
timedatectl

# Check hardware clock (if needed)
hwclock --show
```

**Fix:** Correct the time and timezone using `timedatectl set-timezone` or `ntpdate`.

---

### 2️⃣ **Verify the Crontab Entry**
Ensure the job is correctly defined and that the syntax is valid.

```bash
# For the current user
crontab -l

# For root (if you edited root's crontab)
sudo crontab -l
```

**Check:**
- The schedule format (minute, hour, day, month, day-of-week).
- The absolute path to the command/script.
- That the command works when run manually (e.g., `/path/to/script.sh`).
- Redirection: add `>> /tmp/cron.log 2>&1` to capture output and errors.

**Example of a robust entry:**
```
0 2 * * * /home/user/backup.sh >> /var/log/backup.log 2>&1
```

---

### 3️⃣ **Examine System Logs**
Cron logs its actions to the system log. On most Linux distributions, the logs are in:

```bash
# Check cron logs (RHEL/CentOS/Fedora)
sudo tail -f /var/log/cron

# Or (Debian/Ubuntu)
sudo grep CRON /var/log/syslog

# Older systems may log to /var/log/messages
sudo grep CRON /var/log/messages
```

Look for entries like:
- `(root) CMD (your command)` – confirms cron attempted to run it.
- `(root) MAIL (mailed 1 byte of output)` – indicates output was mailed; check your mail.
- `(root) ERROR (getpwnam() failed)` – user doesn't exist or shell issues.

---

### 4️⃣ **Check User Permissions & Shell**
- The user under which the job runs must have execute permissions on the script and its directory.
- The user's shell must be valid (e.g., `/bin/bash`). Check `/etc/passwd`.
- If the job runs a script, ensure it has the shebang line (`#!/bin/bash`) and is executable (`chmod +x script.sh`).

---

### 5️⃣ **Environment Variables**
Cron runs with a minimal environment (no `PATH` as you expect). Always use **absolute paths** to commands (e.g., `/usr/bin/python3` instead of `python3`). You can also set `PATH` at the top of the crontab:

```
PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=your@email.com
```

Or source your `.bashrc` inside the script:
```bash
source /home/user/.bashrc
```

---

### 6️⃣ **Check for Overlapping Jobs or Resource Limits**
- If the job takes longer than the schedule interval, the next instance may not start. Use `flock` to prevent overlaps.
- Check system load; cron may delay execution if the system is under heavy load.

---

### 7️⃣ **Test with `run-parts` (if using cron.daily/hourly)**
If your job is placed in `/etc/cron.daily/` or similar, you can test it manually:

```bash
sudo run-parts --test /etc/cron.daily
```

---

### 8️⃣ **Verify Systemd Timers (if cron is replaced)**
On newer systems, cron may be replaced by systemd timers. Check if the service is active:

```bash
sudo systemctl status cron
sudo systemctl status crond   # for RHEL
```

---

### 9️⃣ **Check Disk Space & Inodes**
If `/var` or `/tmp` is full, cron may fail to write logs or lock files.

```bash
df -h
df -i
```

---

### 🔟 **Mail Delivery (if output is not logged)**
Cron mails any output to the user. Check local mail:

```bash
mail
# or
cat /var/mail/$USER
```

If mail is not delivered, ensure `postfix` or `sendmail` is running, or redirect output to a log file as shown in step 2.

---

## 📋 Quick Checklist Summary

| Step | Action |
| :--- | :--- |
| 1 | Check system time and timezone. |
| 2 | Verify crontab entry (crontab -l). |
| 3 | Check `/var/log/cron` or `/var/log/syslog` for errors. |
| 4 | Ensure script is executable and paths are absolute. |
| 5 | Set PATH or source profile in script. |
| 6 | Check disk space and system load. |
| 7 | Test the command manually as the same user. |
| 8 | Look for mail (`mail` command). |
| 9 | Verify cron service is running (`systemctl status cron`). |
| 10 | If using SELinux, check audit logs (`ausearch -m avc`). |

By following these steps, you will almost always find the root cause of a failed cron job.
